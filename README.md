# accel-virt

A paravirtual GPU for Windows guests on QEMU/KVM, built spec-first.

Three things get built here:

- **`rvkgpu.sys`** — a WDDM 3.2 kernel-mode display miniport for the guest,
  which speaks virtio-gpu.
- **`virtio-gpu-rvk-pci`** — a custom in-process QEMU device that owns the
  transport, memory mapping, fences, scanout and host execution.
- **the wire protocol** between them.

Command serialization is generated here, by the Khronos-registry generator
vendored in `tools/codegen/` and committed under `src/proto/generated/`. D3D is translated in the guest by
vkd3d-proton and DXVK, which are ordinary Vulkan clients. The design is written
up in [`docs/kb/11-implementation-plan.md`](docs/kb/11-implementation-plan.md),
on top of a WDDM 3.2 knowledge base in [`docs/kb/`](docs/kb/) derived from the
WDK headers and from reverse engineering Microsoft's shipping binaries.

## Why the WDDM version history is the plan

The driver always declares `DXGKDDI_INTERFACE_VERSION_WDDM3_2` (`0x11007`) and
always builds against WDDM 3.2 headers, because **Windows 11 will not load a
driver that declares an older level.** You cannot ship a WDDM 1.0 driver as a
checkpoint.

What the version history gives instead is a dependency-ordered curriculum. Each
level added features that build on the previous ones, so implementing them in
order means never building on something that is not there yet. Capabilities —
not the declared version — gate what is live, so every level is a loadable,
testable checkpoint.

Two consequences worth knowing before you start:

- Some early features are **deliberately throwaway**. Feature 009 uses physical
  addressing and `DxgkDdiPatch`; feature 017 replaces both with GPU virtual
  addressing and `DxgkDdiPatch` is never called again. That is on purpose: 009
  proves the record → submit → fence pipeline with the least machinery.
- Some features are **deliberately never implemented**. Overlays, palettes and
  swizzling ranges are legacy; the WDDM 3.2 SR-IOV and partitioning family
  describes mediated hardware passthrough, which this design is not. The
  roadmap marks these `stub` or `skip`, and the stub is tested like anything
  else.

## Working in this repo

The spec-kit flow, as Claude Code skills:

```
/speckit-constitution   amend the rules
/speckit-specify        write or refine a feature spec
/speckit-clarify        de-risk ambiguity before planning
/speckit-plan           implementation plan for one spec
/speckit-tasks          break the plan into tasks
/speckit-implement      execute
/speckit-analyze        cross-artifact consistency check
```

The autogenerated block in each `spec.md` comes from `tools/features.py` via
`tools/gen_specs.py`; prose written below it is preserved across regeneration.

## Build and test

Everything this repository needs is in it, or fetched into it by pinned hash.

```bash
tools/fetch_windows_kit.sh      # once: WDK/SDK header + import-library subset
tools/fetch_khronos_registries.py  # once: vk.xml, gl.xml, cl.xml, pinned by hash
                                # into third_party/windows-kit/ (not committed)

cmake -S . -B build -G Ninja -DCMAKE_CXX_COMPILER=clang++
cmake --build build             # host core, test binaries, AND rvkgpu.sys
ctest --test-dir build          # the fast gates, a few seconds

tools/gate.sh                   # the full verdict, four configurations
```

| Configuration | Directory | Gates in its `ctest` |
|---|---|---|
| default | `build/` | unit tests under ASan+UBSan, `design_rules`, `symbol_tests`, `driver_image`, `self_contained`, and one `tools_<module>` per `tests/tools` module (label `tools`; the guest runner's in 12 shards) - `ctest -LE tools` is the fast loop |
| coverage | `build-coverage/` | the unit tests again for their profiles, plus `coverage_gate`: 100% branches of `src/core`, `src/device`, `src/proto`, and the `AV_UNTESTABLE` ratchet |
| fuzz | `build-fuzz/` | the gate runs only `fuzz_<target>_smoke` (label `fuzz`): 60 s per target (`AV_FUZZ_SECONDS`) |
| guest | `build-guest/` | `run_guest_suite.py` in a real Windows guest when `AV_GUEST_IMAGE` names a prepared image: the package installed under Driver Verifier, the adapter started on `rvkgpu`, and `rvktest.exe`'s 23 scenarios on the echo executor; then one more boot, `build-guest-real/`, on the real executor for `--rvk --opengl`, with `--vulkan` and `--opencl` added when their pinned runtime and loader have been fetched. Required before a merge (feature 037) |
| qemu | `build-qemu/` | `librvk_device.a`, QEMU 11.1.1 patched with `virtio-gpu-rvk-pci` (`tools/fetch_qemu.sh`, `tools/build_qemu.sh`), `qemu_smoke` (the PCI function a guest sees, the realize failures) and `qemu_virtio_gpu` (the virtio-gpu suites, stock and rvk side by side) |

### Running the device

```bash
tools/host/list_gpus.py                     # the host's Vulkan devices, by UUID
tools/host/list_gpus.py --qemu              # one -device argument per GPU
QEMU_MODULE_DIR=build-qemu/qemu build-qemu/qemu/qemu-system-x86_64 \
    -enable-kvm -m 8G -device virtio-gpu-rvk-pci,host-gpu=auto ...
tools/host/list_gpus.py --libvirt           # the same for a libvirt domain
```

`host-gpu` is `auto` (the first Vulkan device) or a device UUID; a malformed or
absent one fails to start with the reason. The distro QEMU cannot load the
modules: its compiled-in module table has no entry for the new device types.

`cmake --build build` compiles `src/core` twice: for the host tests, and with
`clang-cl /kernel` against the Windows kit, linked into `rvkgpu.sys`. A core
change that would not build in the guest kernel - a hosted header, a C runtime
call, `new`, `throw`, `typeid` - fails the build.

`src/core/memory/gpu_virtual_address_space.cpp` with its `Alignment` and `ByteRange`
value classes is the worked example of the standard the constitution demands:
**100% region, function, line and branch coverage**, invariants asserted after
every mutation, an allocation-failure sweep, IRQL ceilings enforced by the
injected mock, a hostile-input sweep, and a fuzz target.

The design standard is in [`CLAUDE.md`](CLAUDE.md), installed by
`decrapify-cpp` and adapted for freestanding kernel-mode C++: every unit of
behaviour is a class that owns state, dependencies injected at construction, no
static member functions, no stateless classes, no free-function dumping
grounds. `tools/check_design.py` enforces it.
