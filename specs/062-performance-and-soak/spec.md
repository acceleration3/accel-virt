# Feature Specification: Performance, stability and soak

**Feature Branch**: `062-performance-and-soak`

**Created**: 2026-09-11

**Status**: Draft

**Feature ID**: 062 · **Status**: `implement` · **Depends on**: 040, 042, 059, 061

Per-API benchmarks against the same host GPU natively with recorded
thresholds, hours-long soak runs under host stalls, memory pressure and TDR
injection, and leak accounting in the guest and the device, all run by the in-
guest runner and held as ratchets.

### Status meaning

Build it, test it to the constitution's standard, and report the capabilities it enables.

### Design rules — binding on this feature

Constitution Principle III and [`CLAUDE.md`](../../CLAUDE.md). Restated here because it is checked at review, not assumed:

- **Every unit of behaviour is a class that owns state.** No static member functions. No stateless class used as a namespace. No free function outside the two ABI boundaries (`DxgkDdi*` entry points in `src/core/ddi/`, and `extern "C"` entry points), each one line with no logic.
- If functions thread the same handle, buffer, bounds or platform through their parameters, **that parameter is a member**. Make it a class and inject its dependencies at construction.
- Name the classes this feature adds before writing them, and say which kind each is: an **object class** (one instance per real thing) or a **system class** (a long-lived service owning a collection).
- Dependencies injected at construction. No global, no singleton, no file-scope state.
- Data members private, trailing underscore. Classes `PascalCase`, methods and locals `snake_case`. No `Manager`, `Helper`, `Utils`, `Handler`, `Impl`, `process()`, `handle()`.
- One class per header, named for it. A header declares; it does not define. One responsibility per class, statable without an "and".
- Errors are `av::Status` values. No exceptions, no RTTI, no C++ standard library, no `new`/`delete` (placement new only in `ObjectStorage`). Cleanup is RAII via `ScopeExit`, never repeated per branch.
- Fallible construction is two-phase: trivial constructor, `initialize(...)` returning `Status`.
- Every public method declares its IRQL ceiling via `platform_.require_irql_at_most(...)`.

### Test requirements

Constitution Principle III applies in full. Concretely, this feature is not done until:

- every branch of every function it adds to `src/core`, `src/device` or `src/proto` is covered, or marked `AV_UNTESTABLE` with a justification;
- each stateful module it adds exports an invariant function that tests call after **every** mutation;
- every function it adds that reads bytes from outside its own address space has a hostile-input table test and a libFuzzer target with a committed corpus;
- the allocation-failure sweep passes: with each allocation site failed in turn, no crash and no leak;
- IRQL annotations are present and the mock's IRQL checker is satisfied;
- `tools/check_symbol_tests.py` reports no untested exported symbol.

## User Scenarios & Testing *(mandatory)*

<!-- Written by /speckit-specify or by hand. The autogen block above is regenerated by tools/gen_specs.py; everything below is preserved. -->

Users: the project's developers and anyone deciding whether rvkgpu is good
enough to use daily. They need numbers - how fast each API is against the same
host GPU without a VM, and how long the guest runs under abuse before something
leaks, stalls or crashes - measured the same way every time and held so that a
regression fails the gate instead of being noticed months later.

### User Story 1 - Performance against native, per API (Priority: P1)

**Independent Test**: `tools/guest/run_guest_suite.py` runs the benchmark set in
the guest, the same benchmarks run natively on the host GPU, and a report gives
each benchmark's guest-to-native ratio; the run fails when a ratio falls below
its recorded threshold.

**Acceptance Scenarios**:

1. **Given** a benchmark set covering Vulkan, OpenGL, OpenCL, D3D11 and D3D12
   through the Microsoft runtime and through DXVK and vkd3d-proton, **When** it
   runs in the guest and natively, **Then** the report lists frames per second
   or throughput, frame-time percentiles and the ratio for each.
2. **Given** a recorded threshold per benchmark and host GPU, **When** a ratio
   drops below it, **Then** the run fails naming the benchmark; when it rises,
   the threshold can only be raised, like the `AV_UNTESTABLE` ratchet.
3. **Given** the submission path, **Then** per-submit cost, doorbell-to-worker
   latency and fence-to-wake latency are reported from both guest and device.

### User Story 2 - Hours of abuse without a leak or a hang (Priority: P1)

**Independent Test**: a soak run of configurable length (default four hours)
cycles workloads on every API while the runner injects host stalls, memory
pressure and TDRs; at the end the guest's pool tag accounting and the device's
object counts return to their baseline and no bugcheck, device loss outside an
injected fault, or QEMU exit occurred.

**Acceptance Scenarios**:

1. **Given** a stalled host executor thread for longer than the TDR delay,
   **When** the guest's watchdog runs, **Then** `QueryEngineStatus` reports no
   host progress, only the stalled context's device is reset, and the workload
   resumes.
2. **Given** a stall shorter than the TDR delay, **Then** no TDR occurs, because
   engine status reflects host progress rather than ring occupancy.
3. **Given** allocations beyond the adapter's budget, **Then** eviction and
   re-residency keep every application running, if slower.
4. **Given** an injected fault on one context every few minutes, **Then** that
   context recovers and every other context is unaffected.
5. **Given** the end of the soak, **Then** `rvkg` pool tag usage, device-side
   contexts, blobs and workers, and host GPU memory are back at the baseline
   taken before the workloads.

### User Story 3 - Results are comparable over time (Priority: P2)

**Independent Test**: two runs of the same build on the same host produce
results within the recorded noise band; the report records host GPU, driver
versions, QEMU and guest build so results are only compared like with like.

**Acceptance Scenarios**:

1. **Given** a run, **Then** its report is written to the work directory with
   the full environment and appended to a history the thresholds are derived
   from.
2. **Given** a different host GPU, **Then** its thresholds are separate.

### Edge Cases

- The host OOM-kills QEMU during a soak: the run fails, names the kill from
  QEMU's exit status and the host log, and collects the guest's diagnostics
  from a rescue boot.
- A benchmark cannot run natively on the host (a Windows-only title): it is
  compared against its own history, not a native ratio.
- Thermal throttling on a laptop host: the report records host GPU temperature
  and frequency so a throttled run is visible, not a false regression.
- A leak smaller than the accounting resolution: a longer soak mode repeats the
  cycle until growth per cycle is measurable or provably zero.
- The guest bugchecks mid-soak: the runner's panic capture names it and the run
  fails with the dump collected.

## Requirements *(mandatory)*

- **FR-001**: The benchmark and soak sets run from the in-guest runner with one
  command each, and on the host natively where the benchmark exists there.
- **FR-002**: Thresholds are per benchmark and per host GPU, stored in the
  repository, and may only ratchet upward without a spec change.
- **FR-003**: Stall, memory-pressure, fault and TDR injection are driven from
  the host side - the device and the runner - never by modifying the guest
  driver.
- **FR-004**: Leak accounting covers guest pool tags, D3DKMT object counts,
  device-side object counts and host GPU memory, sampled before and after.
- **FR-005**: `QueryEngineStatus` and TDR decisions are validated against real
  host stalls: a stall under the TDR delay never resets, one over it resets only
  the affected device.
- **FR-006**: Every report records the environment needed to compare it: host
  GPU and driver, QEMU build, guest build, package version, and host thermal
  state.
- **FR-007**: A failing soak collects the same diagnostics as a failing suite
  run: event logs, dumps, driver and device logs.

## Success Criteria *(mandatory)*

- **SC-001**: On the two-GPU development host, a four-hour soak completes with
  no bugcheck, no unexpected device loss, no QEMU exit and every counter back at
  baseline.
- **SC-002**: Every benchmark in the set has a recorded threshold, and an
  artificial slowdown injected in the device fails the performance run.
- **SC-003**: Repeated runs of one build fall within the recorded noise band.

## Assumptions

- Features 048, 054 and 059 provide the application suites the benchmarks are
  drawn from; feature 049 provides the user-mode submission path measured here.
- The host can run the native half of the benchmark set (Vulkan, OpenGL and
  OpenCL natively; D3D through the same translation layers under Wine where no
  Linux-native equivalent exists).
- Soak length is a parameter; the gate runs a short soak, a scheduled run the
  full one.

## Out of Scope

- Competitive comparison with other virtual GPU solutions.
- Tuning the host GPU driver or QEMU's own scheduling.
- Power efficiency measurements.
