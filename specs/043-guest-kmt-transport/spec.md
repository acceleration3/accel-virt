**Feature ID**: 043 · **Status**: `implement` · **Depends on**: 041, 024, 034, 063

The guest half of the seam: a user-mode transport carrying this project's
generated Vulkan, OpenGL and OpenCL encoders - a per-process link shared by
all three APIs, synchronous and asynchronous commands, command streams, a
reply area, a blob arena of host-visible memory, fences and completed sequence
numbers - built from an rvk context per sub-API, its ring and doorbell, fence
waits that sleep instead of polling, and allocations from feature 041.
Portable logic tested on Linux over MockKmt and the loopback rig.

### Status meaning

Build it, test it to the constitution's standard, and report the capabilities it enables.

### Note

The transport interface is this repository's, defined here; the generated
client dispatch is handed one. There is no external interface to implement.

### Design rules — binding on this feature

Constitution Principle III and [`CLAUDE.md`](../../CLAUDE.md). Restated here because it is checked at review, not assumed:

- **Every unit of behaviour is a class that owns state.** No static member functions. No stateless class used as a namespace. No free function outside the two ABI boundaries (`DxgkDdi*` entry points in `src/core/ddi/`, and `extern "C"` entry points), each one line with no logic.
- If functions thread the same handle, buffer, bounds or platform through their parameters, **that parameter is a member**. Make it a class and inject its dependencies at construction.
- Name the classes this feature adds before writing them, and say which kind each is: an **object class** (one instance per real thing) or a **system class** (a long-lived service owning a collection).
- Dependencies injected at construction. No global, no singleton, no file-scope state.
- Data members private, trailing underscore. Classes `PascalCase`, methods and locals `snake_case`. No `Manager`, `Helper`, `Utils`, `Handler`, `Impl`, `process()`, `handle()`.
- One class per header, named for it. A header declares; it does not define. One responsibility per class, statable without an "and".
- Errors are `av::Status` values. No exceptions, no RTTI, no C++ standard library, no `new`/`delete` (placement new only in `ObjectStorage`). Cleanup is RAII via `ScopeExit`, never repeated per branch.
- Fallible construction is two-phase: trivial constructor, `initialize(...)` returning `Status`.
- Every public method declares its IRQL ceiling via `platform_.require_irql_at_most(...)`.

## User Scenarios & Testing *(mandatory)*

Users: this project's guest-side clients - the Vulkan ICD (045), the OpenGL
driver (050) and the OpenCL ICD (052). Their encoders are generated by feature
063's vendored generator over this repository's `WireWriter`, `WireReader` and
`WireArena`. What the generator does not write is the path from an encoded
command to the host and back, and this feature is that path: D3DKMT for setup,
an rvk context's ring and doorbell for commands, rvk fences for completion, the
wire `docs/protocol.md` describes throughout.

**What changed, and why this spec was rewritten.** This feature was first
written as a home for render-server's Windows drivers: implement its abstract
`Transport`, ask it to let its per-process link be built over a transport handed
to it, and take its test suite as the acceptance. Feature 063 settled that this
project takes render-server's registry generators and nothing else. The clients
above this transport are generated here, the wire they speak is this project's,
and the transport interface is this repository's to define. Nothing in this
feature waits on another project.

### User Story 1 - The generated encoders reach the host through rvkgpu (Priority: P1)

**Independent Test**: on Linux, the transport's portable core runs over `MockKmt`
and the L4 loopback rig with the device core and the echo executor; a scripted
client issues synchronous, asynchronous, batched and stream commands and reads
back replies and sequence numbers.

**Acceptance Scenarios**:

1. **Given** a process in which the first generated client loads, **When** it
   asks for its link, **Then** the transport opens the rvkgpu adapter by LUID,
   creates a device, and one rvk context per sub-API the process uses; a second
   client in the same process shares the same link.
2. **Given** a link, **When** a client sends a synchronous command, **Then** it is
   written to the context's ring inside a batch, the doorbell is rung, and the
   call returns with the answer the executor wrote to the context's reply slot.
3. **Given** asynchronous commands, batches and command streams, **When** they are
   sent, **Then** they are ordered on the ring under fence ids that only
   increase, the last published and the last completed sequence numbers are
   reported, and the completed number comes from the context's fence page.
4. **Given** a client waiting for a sequence number or a fence, **When** it is not
   yet reached, **Then** the thread sleeps on a monitored fence wait
   (`D3DKMTWaitForSynchronizationObjectFromCpu`) and wakes on the interrupt - it
   never polls.

### User Story 2 - A blob arena of host-visible memory (Priority: P1)

**Independent Test**: over the loopback rig, the transport allocates blobs, maps
them, and the device's view of a written byte matches; a 32-bit view is checked
to lie below 4 GiB.

**Acceptance Scenarios**:

1. **Given** a client asking for blob memory, **When** the transport allocates
   it, **Then** it is an allocation from feature 041 mapped into the process, and
   the bytes the executor reads on the host are the bytes the client wrote.
2. **Given** a 32-bit process, **When** a low view is requested, **Then** it lies
   below 4 GiB or the allocation fails with a status.
3. **Given** retired blobs, **When** their fences complete, **Then** the transport
   releases the allocations.

### User Story 3 - Faults, TDR and device loss reach the client (Priority: P1)

**Independent Test**: `MockKmt` scripts a faulted fence page, a device-lost status
from every D3DKMT call, and a doorbell disconnect; the transport reports each
through its connected state and failing sends.

**Acceptance Scenarios**:

1. **Given** a context the device faults, **When** the client next sends, **Then**
   the send fails, the link reads as disconnected, and the client can report
   device lost.
2. **Given** a TDR on the adapter, **When** the client waits, **Then** the wait
   returns, and a new link can be created once the adapter recovers.

### Edge Cases

- The ring is full: a send waits on the fence of the oldest unconsumed record,
  bounded by a timeout, never overwrites.
- A reply larger than the reply slot holds: the slot reads back the length the
  answer required and no bytes, and the send fails with a status carrying that
  length, so the caller can ask again with room for it.
- The fence page or reply slot holds hostile values (a size past the slot, a
  completed fence that goes backwards or exceeds what was submitted, a required
  length beyond capacity, a fault flag that clears): the transport treats the
  context as faulted, never reads outside its mapping.
- The adapter is removed or disabled while a process holds a link: every call
  fails with device lost; nothing touches unmapped memory.
- The doorbell is disconnected (suspend, TDR): stores land on a harmless page and
  the transport falls back to `D3DKMTSubmitCommand` until reconnected.
- Several threads in one process load the clients at once: exactly one link is
  created and every client shares it.
- Budget exceeded when allocating blobs: allocation fails with an out-of-memory
  status the client maps to its API's error.

## Requirements *(mandatory)*

- **FR-001**: The transport interface is defined in this repository and is what
  the generated client dispatch is handed. It sends a command and waits for its
  answer, sends one without waiting, sends a batch, sends a command stream,
  reports its reply capacity, reports the last published and the last completed
  sequence number, reports whether the link is connected, names itself, and
  hands out, retires and low-views blob memory.
- **FR-002**: *Dropped.* It required render-server to let its per-process link be
  constructed over a supplied transport; this project uses none of
  render-server's runtime, so there is nobody to ask and nothing to fit.
- **FR-003**: Portable decision logic lives in this repository's guest code, is
  tested on Linux over `MockKmt` and the loopback rig to constitution IV, and a
  Windows shim translates to gdi32 only.
- **FR-004**: One rvk context per sub-API per process; the context's capset
  sub-API is Vulkan, OpenGL or OpenCL as the client requests.
- **FR-005**: Every value read from a mapped area is validated before use; a
  violation faults the link.
- **FR-006**: Waiting uses rvk fences through D3DKMT; no busy polling, no
  fixed-period parking.
- **FR-007**: Setup uses `D3DKMTSubmitCommand` doorbell-less submission; feature
  049 moves the hot path to WDDM doorbells.
- **FR-008**: Presentation is not the transport's; it goes through the KMD
  (046, 051).
- **FR-009**: What the transport publishes is the wire `docs/protocol.md`
  describes - a batch header with its magic, length and increasing fence id, the
  commands inside it framed by id and size with the reply flag on the one whose
  answer is wanted - and the command ids are the ones feature 063's generator
  assigns.

## Success Criteria *(mandatory)*

- **SC-001**: The L4 loopback suite drives the transport through a round trip, a
  batch, a command stream, an answer too large for the reply slot, a faulted
  context, a hostile mapping and a full ring, and passes.
- **SC-002**: 100% branch coverage of the transport core; a hostile-mapping table
  test and a fuzz target for the reply-slot and fence-page readers.
- **SC-003**: No thread in a waiting process consumes CPU while waiting.
- **SC-004**: `tools/guest/run_guest_suite.py` runs a scenario in a real guest
  that creates a context per sub-API through the transport, submits, waits and
  completes, and the run reports no failure. The same path over a live host
  executor is feature 044.

## Assumptions

- Features 024 and 041 provide mappable rings, fence pages and host-visible
  allocations.
- Feature 063's generator emits the client dispatch and the ICD entry points for
  each API; this feature supplies the transport they are handed. How that
  parameter is spelled in the emitted sources is settled with the generator,
  which this project owns.

## Out of Scope

- Which commands each API covers, which the generator's profiles decide (063).
- The ICDs and the driver that sit on this transport (045, 050, 052).
- The host executor that runs what the transport carries (042).
- Doorbells and native fences on the hot path (049).
- Cross-process sharing (053).
