# Feature Specification: One installable driver package

**Feature Branch**: `061-driver-package`

**Created**: 2026-09-11

**Status**: Draft

<!-- AUTOGEN:BEGIN -->

**Feature ID**: 061 · **Status**: `implement` · **Depends on**: 047, 054, 055, 057, 060, 064

A single driver package that installs the KMD, the UMD and the Vulkan, OpenGL
and OpenCL drivers in 64-bit and WoW64 32-bit forms, with the Khronos Vulkan
and OpenCL loaders where Windows has none, registered through the adapter as a
DCH-compliant package does, upgraded and removed cleanly, and refusing a
device whose protocol version it cannot speak.

### Status meaning

Build it, test it to the constitution's standard, and report the capabilities it enables.

### Design rules — binding on this feature

Constitution Principle III and [`CLAUDE.md`](../../CLAUDE.md). Restated here because it is checked at review, not assumed:

- **Every unit of behaviour is a class that owns state.** No static member functions. No stateless class used as a namespace. No free function outside the two ABI boundaries (`DxgkDdi*` entry points in `src/core/ddi/`, and `extern "C"` entry points), each one line with no logic.
- If functions thread the same handle, buffer, bounds or platform through their parameters, **that parameter is a member**. Make it a class and inject its dependencies at construction.
- Name the classes this feature adds before writing them, and say which kind each is: an **object class** (one instance per real thing) or a **system class** (a long-lived service owning a collection).
- Dependencies injected at construction. No global, no singleton, no file-scope state.
- Data members private, trailing underscore. Classes `PascalCase`, methods and locals `snake_case`. No `Manager`, `Helper`, `Utils`, `Handler`, `Impl`, `process()`, `handle()`.
- One class per header, named for it. A header declares; it does not define. One responsibility per class, statable without an "and".
- Errors are `av::Status` values. No exceptions, no RTTI, no C++ standard library, no `new`/`delete` (placement new only in `ObjectStorage`). Cleanup is RAII via `ScopeExit`, never repeated per branch.
- Fallible construction is two-phase: trivial constructor, `initialize(...)` returning `Status`.
- Every public method declares its IRQL ceiling via `platform_.require_irql_at_most(...)`.

### Test requirements

Constitution Principle III applies in full. Concretely, this feature is not done until:

- every branch of every function it adds to `src/core`, `src/device` or `src/proto` is covered, or marked `AV_UNTESTABLE` with a justification;
- each stateful module it adds exports an invariant function that tests call after **every** mutation;
- every function it adds that reads bytes from outside its own address space has a hostile-input table test and a libFuzzer target with a committed corpus;
- the allocation-failure sweep passes: with each allocation site failed in turn, no crash and no leak;
- IRQL annotations are present and the mock's IRQL checker is satisfied;
- `tools/check_symbol_tests.py` reports no untested exported symbol.

## User Scenarios & Testing *(mandatory)*

<!-- Written by /speckit-specify or by hand. The autogen block above is regenerated by tools/gen_specs.py; everything below is preserved. -->

Users: whoever installs the guest driver - a person setting up a Windows VM,
or the in-guest runner - who needs one package that makes rvkgpu a complete
GPU: the kernel driver, the Direct3D user-mode driver and the Vulkan, OpenGL and
OpenCL drivers, for 64-bit and 32-bit applications, installed, upgraded and
removed the way Windows expects a display driver to be.

### User Story 1 - One package installs everything (Priority: P1)

**Independent Test**: the in-guest runner installs the package with
`pnputil /add-driver <inf> /install` into a clean prepared image, and a guest
program confirms the KMD started and that Direct3D, Vulkan, OpenGL and OpenCL
each load the rvkgpu driver for the adapter in a 64-bit and a 32-bit process.

**Acceptance Scenarios**:

1. **Given** a clean guest, **When** the package installs, **Then** every file -
   `rvkgpu.sys`, `rvkumd.dll`, the Vulkan, OpenGL and OpenCL drivers and their
   32-bit builds - lands in the DriverStore and nowhere else, and the adapter
   starts with no problem code.
2. **Given** the installed adapter, **When** the adapter's software key is read,
   **Then** it carries `UserModeDriverName`, `VulkanDriverName`,
   `OpenGLDriverName` and `OpenCLDriverName`, each with its `Wow` counterpart,
   written by the INF's AddReg and pointing into the DriverStore.
3. **Given** a 32-bit and a 64-bit test program for each API, **When** each runs,
   **Then** the system loader for that API (D3D runtime, Vulkan loader,
   `opengl32.dll`, OpenCL ICD loader) loads the rvkgpu driver of matching
   bitness and renders or computes on the host GPU.
4. **Given** the global Khronos registry keys, **Then** the package writes none
   of them.

### User Story 2 - Upgrade and removal are clean (Priority: P1)

**Independent Test**: the in-guest runner installs package version N, starts
applications on every API, installs version N+1, and after the reboot or
restart Windows asks for, checks only N+1's files are loaded; then removes the
package and checks no rvkgpu file, service or registration remains and the
guest falls back to Microsoft Basic Display.

**Acceptance Scenarios**:

1. **Given** version N installed with applications holding the adapter, **When**
   N+1 installs, **Then** the install either restarts the driver in place or
   requests a reboot, and never leaves N's user-mode drivers paired with N+1's
   kernel driver.
2. **Given** the desktop running on the adapter, **When** the package is
   uninstalled with `pnputil /delete-driver /uninstall`, **Then** the desktop
   moves to Basic Display, the device reports no problem, and a reboot leaves no
   rvkgpu file in the DriverStore.
3. **Given** a downgrade to an older package, **Then** it installs only if its
   protocol range includes the device's.

### User Story 3 - The package refuses what it cannot drive (Priority: P2)

**Independent Test**: the harness offers the driver a capset whose protocol
version is outside the range it speaks; the adapter fails to start with a
logged reason and a Code 10 instead of starting and failing later.

**Acceptance Scenarios**:

1. **Given** a device offering only a newer major protocol version, **When** the
   driver starts, **Then** it refuses with a status and a log line naming both
   versions.
2. **Given** a device offering a sub-API the user-mode drivers were not built
   for, **Then** that API's driver reports no device and the others still work.
3. **Given** a stock `virtio-gpu-pci`, **Then** the package does not bind to it
   (the hardware id includes the rvk subsystem).

### Edge Cases

- A 32-bit-only application on a 64-bit guest: the WoW64 drivers serve it with
  host-visible views below 4 GiB.
- A second rvkgpu adapter appears after install: it uses the same DriverStore
  package without reinstalling.
- The package is installed while a previous Looking Glass or ivshmem-based
  render-server install left global Khronos keys: the rvkgpu registration is
  used for rvkgpu adapters and the stale global entries are reported, not
  deleted.
- Install on a Windows build older than 24H2: the INF's target decoration
  refuses it.
- Test signing off: installation fails with the signature error, not a partial
  install.

## Requirements *(mandatory)*

- **FR-001**: One INF, one catalog: the package installs the KMD, the UMD and the
  three API drivers in 64-bit and WoW64 32-bit forms, all copied to the
  DriverStore (`DIRID 13`), with `PnpLockdown`.
- **FR-002**: User-mode drivers are registered only through the adapter's
  software key with the `*DriverName` and `*DriverNameWow` values; no global
  registry key and no file outside the DriverStore.
- **FR-003**: The driver refuses to start on a device whose capset protocol
  version it cannot speak, logging both versions at the point of decision.
- **FR-004**: Every binary in the package is built by the default configuration
  and checked by an image gate: machine, subsystem, imports only from modules
  the guest has, and no header flag the loader rejects.
- **FR-005**: A package test in `tests/tools` checks the INF names every file
  the build produces, copies nothing the build does not produce, and registers
  each driver name exactly once.
- **FR-006**: The in-guest runner installs the package, not loose files, and
  its provision stages test-sign the catalog.
- **FR-007**: The package version, the driver version and the protocol range it
  speaks are one number set in one place.
- **FR-008**: Where the guest has no Khronos Vulkan loader (`vulkan-1.dll`) or
  OpenCL ICD loader (`OpenCL.dll`), the package installs the pinned Khronos
  builds for x64 and x86; where a newer one is present, it is left in place and
  the package's drivers work with it; removal never deletes a loader another
  package installed.

## Success Criteria *(mandatory)*

- **SC-001**: On a clean prepared image, one install yields all four APIs in
  64-bit and 32-bit processes on the adapter.
- **SC-002**: Upgrade and removal runs leave no stale file, service or
  registration, verified by the runner.
- **SC-003**: The package gate fails the build when a produced binary is not in
  the INF, or an INF file is not produced.

## Assumptions

- Test signing in the guest, as the in-guest runner prepares it, is the signing
  model; Windows 11 24H2 or later is the target.
- The ICDs and the UMD exist in 64-bit and 32-bit forms from features 045-057.
- The Vulkan, OpenGL, OpenCL and D3D loaders on 24H2 honour the adapter's
  driver-name registration.

## Out of Scope

- Production signing: EV certificates, attestation signing, WHQL submission.
- An installer executable or Windows Update distribution.
- ARM64 guests.
- Removing registrations other products left behind.
