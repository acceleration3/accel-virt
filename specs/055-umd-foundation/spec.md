# Feature Specification: rvkumd.dll: the user-mode driver and DXGI

**Created**: 2026-09-11

**Feature ID**: 055 · **Status**: `implement` · **Depends on**: 049, 053

The user-mode driver the D3D runtimes load for the adapter: adapter open, the
DXGI DDI (present, blit, resource rotation), adapter identity, memory and
feature levels reported truthfully so DXGI and DXCore enumerate rvkgpu as a
real GPU, and the allocation private data the KMD validates - built on the
same transport as the ICDs.

### Status meaning

Build it, test it to the constitution's standard, and report the capabilities it enables.

### Design rules — binding on this feature

Constitution Principle III and [`CLAUDE.md`](../../CLAUDE.md). Restated here because it is checked at review, not assumed:

- **Every unit of behaviour is a class that owns state.** No static member functions. No stateless class used as a namespace. No free function outside the two ABI boundaries (`DxgkDdi*` entry points in `src/core/ddi/`, and `extern "C"` entry points), each one line with no logic.
- If functions thread the same handle, buffer, bounds or platform through their parameters, **that parameter is a member**. Make it a class and inject its dependencies at construction.
- Name the classes this feature adds before writing them, and say which kind each is: an **object class** (one instance per real thing) or a **system class** (a long-lived service owning a collection).
- Dependencies injected at construction. No global, no singleton, no file-scope state.
- Data members private, trailing underscore. Classes `PascalCase`, methods and locals `snake_case`. No `Manager`, `Helper`, `Utils`, `Handler`, `Impl`, `process()`, `handle()`.
- One class per header, named for it. A header declares; it does not define. One responsibility per class, statable without an "and".
- Errors are `av::Status` values. No exceptions, no RTTI, no C++ standard library, no `new`/`delete` (placement new only in `ObjectStorage`). Cleanup is RAII via `ScopeExit`, never repeated per branch.
- Fallible construction is two-phase: trivial constructor, `initialize(...)` returning `Status`.
- Every public method declares its IRQL ceiling via `platform_.require_irql_at_most(...)`.

Constitution Principle III applies in full. Concretely, this feature is not done until:

## User Scenarios & Testing *(mandatory)*

<!-- Written by /speckit-specify or by hand. The autogen block above is regenerated by tools/gen_specs.py; everything below is preserved. -->

Users: everything in the guest that reaches the GPU through the Microsoft
runtime rather than through a translation layer placed beside it - DWM, DXGI
and DXCore adapter enumeration, Direct2D, Media Foundation's renderers,
browsers - and the developers of features 056 and 057, who need one user-mode
driver the D3D10/11 runtime and D3D12Core both load, with its DXGI half, its
allocation contract with the KMD and its transport already working.
vkd3d-proton and DXVK need none of this (`docs/kb/07-usermode.md`); this
feature exists so the adapter is a first-class GPU.

### How the translation is built — binding on 055, 056, 057 and 064

**DXVK and vkd3d-proton are used as source, not as binaries.** Their
translation code is what turns Direct3D into Vulkan, built into `rvkumd.dll`
so the Vulkan commands it produces cross this project's wire to the QEMU
device. Placing `d3d11.dll`, `d3d12.dll` or `d3d9.dll` beside an application -
what feature 047's probes do to exercise the Vulkan ICD - is a test harness,
not the shipping design, and is not what these features deliver. The source
subset is vendored and pinned the way `tools/codegen/` vendors the Khronos
generator.

### User Story 1 - The runtimes load rvkumd.dll for the adapter (Priority: P1)

**Independent Test**: in the guest, the in-guest runner installs the package
and a probe program creates a D3D11 device and a D3D12 device on the rvkgpu
adapter by LUID; both runtimes load `rvkumd.dll` (64-bit) or its WoW64 build
(32-bit probe), and the probe records which DDI entries were called. On Linux,
the UMD's portable core is driven through the same entries by a fake runtime
built from that recorded sequence.

**Acceptance Scenarios**:

1. **Given** the package is installed, **When** the adapter's software key is
   read, **Then** `UserModeDriverName` and `UserModeDriverNameWow` name the
   64-bit and 32-bit builds of `rvkumd.dll` in the driver store.
2. **Given** a D3D10/11 device is requested, **When** the runtime calls
   `OpenAdapter10_2`, **Then** the UMD opens the adapter, reports the DDI
   interface and version it implements, and returns a function table whose
   every entry is either implemented or returns the documented not-supported
   result.
3. **Given** a D3D12 device is requested, **When** D3D12Core opens the adapter
   through the D3D12 UMD DDI (`d3d12umddi.h`), **Then** the UMD answers the
   calls D3D12Core makes at device creation - the set derived from
   `d3d12core.dll` in `re/ghidra-proj`, not guessed - and device creation
   either succeeds at the feature level feature 057 reports or fails with the
   status D3D12Core expects when 057 is absent.
4. **Given** the UMD is loaded, **Then** it opens the adapter's transport
   (feature 043) once per process and shares it with the ICDs in that process.

### User Story 2 - DXGI and DXCore see a real GPU (Priority: P1)

**Independent Test**: a probe enumerates adapters through
`IDXGIFactory6::EnumAdapterByGpuPreference` and DXCore; the rvkgpu adapter is
listed with its description, vendor/device ids, LUID and dedicated/shared
memory, and is not flagged as a software adapter.

**Acceptance Scenarios**:

1. **Given** the adapter, **When** DXGI queries its description, **Then** the
   name, ids and memory figures come from the capset's GPU identity and the
   KMD's segments, and match what Vulkan reports for the same LUID.
2. **Given** DXCore's attribute queries, **When** it asks for D3D11 or D3D12
   graphics support, **Then** only what features 056 and 057 implement and test
   is claimed.

### User Story 3 - DXGI presents through the UMD (Priority: P1)

**Independent Test**: a windowed and a fullscreen swapchain present frames
through `DXGI_DDI_BASE_FUNCTIONS`; frames reach DWM on WARP (before feature
058) through the KMD present path of feature 046, and the host sees them.

**Acceptance Scenarios**:

1. **Given** a swapchain, **When** DXGI calls `Present`, `Blt`,
   `RotateResourceIdentities` or `SetDisplayMode`, **Then** the UMD performs it
   through the KMD's present and flip DDIs and returns the DXGI status the
   runtime expects.
2. **Given** a present to an occluded or minimized window, **Then** the status
   is the one a hardware driver returns and no frame is lost or duplicated.

### User Story 4 - The KMD distrusts the UMD's private data (Priority: P1)

**Independent Test**: harness scenarios feed the KMD allocation and context
private driver data from a hostile process - truncated, oversized, wrong
version, integer-overflowing sizes, byte-flipped - and a fuzz target covers the
decoder; every case is refused with a status and nothing is written outside
its destination.

**Acceptance Scenarios**:

1. **Given** a valid UMD allocation description, **When** the KMD creates the
   allocation, **Then** the segment, size and blob kind match the description.
2. **Given** any malformed description, **Then** `DxgkDdiCreateAllocation`
   refuses it and logs the refusal once with the offending value.

### Edge Cases

- A 32-bit process under WoW64: the Wow build loads, maps host-visible memory
  below 4 GiB, and shares nothing with the 64-bit build's state.
- The device is removed or reset (TDR): every call after the loss returns
  `DXGI_ERROR_DEVICE_REMOVED` semantics, `GetDeviceRemovedReason` names the
  cause, and a new device on the recovered adapter works.
- DWM restarts: the UMD instance in the new DWM process opens the adapter
  cleanly; state from the old process is gone on the host too.
- The host GPU lacks a capability a feature level needs: the level is not
  reported; DXGI still enumerates the adapter.
- A display mode change arrives during a present: the present completes or
  fails with the status the runtime retries on, never both.
- Two runtimes in one process (D3D11 and D3D12): one transport, two devices.

## Requirements *(mandatory)*

- **FR-001**: `rvkumd.dll` exposes exactly the entry points the D3D10/11
  runtime and D3D12Core load (`OpenAdapter10_2`, the D3D12 UMD open), in 64-bit
  and WoW64 32-bit builds, registered through the adapter's
  `UserModeDriverName` and `UserModeDriverNameWow` values.
- **FR-002**: The minimum DDI set is derived by reverse engineering the calls
  `d3d12core.dll` and the D3D11 runtime make, recorded with the function each
  was read from, and replayed by the fake runtime in the unit tests.
- **FR-003**: Every function-table entry is implemented or returns the
  documented not-supported result; a test asserts each one.
- **FR-004**: Adapter identity, memory and supported feature levels reported
  to DXGI and DXCore come from the capset and the KMD, and never claim more
  than features 056 and 057 implement and test (constitution VI).
- **FR-005**: The DXGI DDI presents through the KMD present path of feature 046
  until feature 058 replaces it with flips of host images.
- **FR-006**: The allocation, resource and context private driver data format
  lives in `src/proto`; the KMD validates it as hostile input with a table test
  and a libFuzzer target.
- **FR-007**: The UMD uses the guest transport of feature 043, one link per
  process shared with the Vulkan, OpenGL and OpenCL drivers.
- **FR-008**: The UMD's decision-making logic is portable C++ tested on Linux
  over a fake runtime and `MockKmt`; the Windows DLL shim is translation only.
- **FR-009**: Device loss is detected from the transport's fault and TDR
  notifications and surfaced on the next call.

## Success Criteria *(mandatory)*

- **SC-001**: A D3D11 and a D3D12 device create on the rvkgpu adapter in the
  guest from 64-bit and 32-bit probes.
- **SC-002**: DXGI and DXCore list rvkgpu as a hardware adapter with the same
  LUID, ids and memory Vulkan reports.
- **SC-003**: The KMD's private-data decoder has 100% branch coverage and a fuzz
  target that survives the smoke run.
- **SC-004**: A DXGI swapchain's frames reach the host display through the
  present path with DWM on WARP.

## Assumptions

- Features 043, 046, 049 and 053 are complete: a working transport, a KMD
  present path, user-mode submission and shared allocations.
- The HLK is not required for this feature; correctness comes from the probe
  scenarios and, from feature 059, the HLK graphics tests as an oracle.

## Out of Scope

- Rendering: resources, shaders and draws are features 056 (D3D10/11) and 057
  (D3D12).
- Flips of host images and dmabuf scanout: feature 058.
- Video decode and encode (DXVA, Media Foundation hardware transforms).
- Direct3D 9 through the Microsoft runtime (the D3D9 UMD DDI): feature 064,
  on the foundation this feature lays.
- Production signing.
