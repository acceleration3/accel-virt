# Feature Specification: Direct3D 10 and 11: the user-mode driver

**Feature Branch**: `056-d3d11-umd`

**Created**: 2026-09-11

**Status**: Draft

**Feature ID**: 056 · **Status**: `implement` · **Depends on**: 055

The D3D10/11 UMD DDI over Vulkan remoting - resources, DXBC shaders translated
to SPIR-V, state, draws and compute, queries and maps - so DWM, Direct2D,
DirectWrite, browsers and applications shipping their own D3D11 run on rvkgpu
through the Microsoft runtime; feature level 11_1 reported only when it is
complete.

### Status meaning

Build it, test it to the constitution's standard, and report the capabilities it enables.

### Design rules — binding on this feature

Constitution Principle III and [`CLAUDE.md`](../../CLAUDE.md). Restated here because it is checked at review, not assumed:

- **Every unit of behaviour is a class that owns state.** No static member functions. No stateless class used as a namespace. No free function outside the two ABI boundaries (`DxgkDdi*` entry points in `src/core/ddi/`, and `extern "C"` entry points), each one line with no logic.
- If functions thread the same handle, buffer, bounds or platform through their parameters, **that parameter is a member**. Make it a class and inject its dependencies at construction.
- Name the classes this feature adds before writing them, and say which kind each is: an **object class** (one instance per real thing) or a **system class** (a long-lived service owning a collection).
- Dependencies injected at construction. No global, no singleton, no file-scope state.
- Data members private, trailing underscore. Classes `PascalCase`, methods and locals `snake_case`. No `Manager`, `Helper`, `Utils`, `Handler`, `Impl`, `process()`, `handle()`.
- One class per header, named for it. A header declares; it does not define. One responsibility per class, statable without an "and".
- Errors are `av::Status` values. No exceptions, no RTTI, no C++ standard library, no `new`/`delete` (placement new only in `ObjectStorage`). Cleanup is RAII via `ScopeExit`, never repeated per branch.
- Fallible construction is two-phase: trivial constructor, `initialize(...)` returning `Status`.
- Every public method declares its IRQL ceiling via `platform_.require_irql_at_most(...)`.

### Test requirements

Constitution Principle III applies in full. Concretely, this feature is not done until:

- every branch of every function it adds to `src/core`, `src/device` or `src/proto` is covered, or marked `AV_UNTESTABLE` with a justification;
- each stateful module it adds exports an invariant function that tests call after **every** mutation;
- every function it adds that reads bytes from outside its own address space has a hostile-input table test and a libFuzzer target with a committed corpus;
- the allocation-failure sweep passes: with each allocation site failed in turn, no crash and no leak;
- IRQL annotations are present and the mock's IRQL checker is satisfied;
- `tools/check_symbol_tests.py` reports no untested exported symbol.

## User Scenarios & Testing *(mandatory)*

<!-- Written by /speckit-specify or by hand. The autogen block above is regenerated by tools/gen_specs.py; everything below is preserved. -->

Users: DWM, Direct2D and DirectWrite, browsers' compositors, Windows' own
applications and any application that ships against the system D3D11 or D3D10
runtime - none of which can have DXVK placed beside them. They need
`rvkumd.dll`'s D3D10/11 DDI to render on the host GPU with the results a
hardware driver gives.

### How the translation is built — binding on 055, 056, 057 and 064

**DXVK and vkd3d-proton are used as source, not as binaries.** Their
translation code is what turns Direct3D into Vulkan, built into `rvkumd.dll`
so the Vulkan commands it produces cross this project's wire to the QEMU
device. Placing `d3d11.dll`, `d3d12.dll` or `d3d9.dll` beside an application -
what feature 047's probes do to exercise the Vulkan ICD - is a test harness,
not the shipping design, and is not what these features deliver. The source
subset is vendored and pinned the way `tools/codegen/` vendors the Khronos
generator.

### User Story 1 - D3D11 applications render correctly (Priority: P1)

**Independent Test**: in the guest, a D3D11 sample suite (clear, textured
geometry, render targets, depth/stencil, blending, instancing, compute,
mipmapped and array textures, MSAA resolve) renders on rvkgpu; each frame is
read back and compared against a reference within a stated tolerance. On
Linux, the translation core runs the same command sequences against the
loopback rig with a mock executor that checks the emitted Vulkan command
stream.

**Acceptance Scenarios**:

1. **Given** a D3D11 device from feature 055, **When** the runtime creates
   buffers, textures, views, samplers and state objects through the D3D11 DDI,
   **Then** each becomes a host object through the Vulkan remoting ring, and
   invalid descriptions the runtime passes through are refused with the status
   the runtime expects.
2. **Given** DXBC shaders the runtime has validated, **When** they are created,
   **Then** they are translated to SPIR-V and run with results identical to
   the reference within tolerance; a shader the translator cannot handle fails
   creation with a logged reason, never at draw time.
3. **Given** draws, compute dispatches, copies, `Map` and `Unmap` with every
   map type, **Then** results and returned data match the reference.
4. **Given** queries (occlusion, timestamp, event), **Then** they complete
   with correct results and `GetData` respects `DONOTFLUSH`.

### User Story 2 - DWM composites on rvkgpu (Priority: P1)

**Independent Test**: after installation the in-guest runner restarts DWM and
checks, through DWM's adapter selection and the KMD's device list, that DWM's
D3D device is on rvkgpu and not on WARP; the desktop renders and the host sees
it.

**Acceptance Scenarios**:

1. **Given** the package and a reboot, **When** DWM starts, **Then** it
   creates its device on rvkgpu and composites every window.
2. **Given** another process's redirected surface, **When** DWM composes it,
   **Then** the shared surface (feature 053) is used without a copy through
   system memory.

### User Story 3 - Direct2D, DirectWrite and browsers (Priority: P2)

**Independent Test**: a Direct2D/DirectWrite sample and Edge rendering a fixed
page with GPU compositing enabled produce frames matching references; the
browser's GPU status page reports hardware acceleration on rvkgpu.

**Acceptance Scenarios**:

1. **Given** Direct2D over D3D11, **When** text and geometry render, **Then**
   output matches within tolerance.
2. **Given** a browser, **Then** its compositor uses the rvkgpu device and no
   fallback to software is logged.

### User Story 4 - Feature level 11_1 claimed only when true (Priority: P1)

**Independent Test**: the reported feature level and each `CheckFeatureSupport`
/ `CheckFormatSupport` answer is backed by a named passing test; a table test
asserts the level drops when the capset lacks a host capability it depends on.

**Acceptance Scenarios**:

1. **Given** a host GPU with every capability 11_1 needs, **Then** 11_1 is
   reported; **given** one without, **Then** the highest complete level is.

### Edge Cases

- Device removed mid-frame (TDR, host fault): calls return device-removed
  semantics; DWM recreates its device and the desktop recovers.
- A mode change or monitor hot-plug during a present.
- WoW64 32-bit applications with large textures: mappings use views below
  4 GiB and fail cleanly when the budget is exhausted.
- `Map` of a resource being written by the host: the wait respects the
  runtime's `DONOTWAIT` flag with `DXGI_ERROR_WAS_STILL_DRAWING`.
- Formats the host GPU cannot sample or render: refused in format support,
  never silently emulated incorrectly.
- Deferred contexts and command lists from several threads.
- D3D10 and D3D10.1 devices on the same DDI.

## Requirements *(mandatory)*

- **FR-001**: `rvkumd.dll` implements the D3D10/11 UMD DDI tables the runtime
  calls for feature levels up to 11_1, derived from the runtime's calls as in
  feature 055.
- **FR-002**: Every resource, view, state, shader, query and command maps to
  host Vulkan objects and commands over the transport; no rendering happens in
  the guest.
- **FR-003**: DXBC is translated to SPIR-V; the observable requirement is that
  every shader the runtime accepts either runs with results identical to the
  reference within tolerance or fails creation with a logged reason. The
  translator is a plan decision.
- **FR-004**: The reported feature level, format support and optional features
  are each backed by a passing test and gated on capset bits (constitution VI).
- **FR-005**: Presentation goes through the DXGI DDI of feature 055.
- **FR-006**: The translation core is portable C++ tested on Linux to the
  constitution's standard, including hostile runtime arguments where the
  runtime does not validate them.
- **FR-007**: Nothing on the draw path allocates guest heap per call or takes
  a kernel transition when user-mode submission (feature 049) is available.

## Success Criteria *(mandatory)*

- **SC-001**: The D3D11 sample suite matches references in the guest.
- **SC-002**: DWM composites on rvkgpu, not WARP, after a clean install.
- **SC-003**: Direct2D and a browser render with hardware acceleration on
  rvkgpu.
- **SC-004**: The HLK D3D11 graphics tests selected in feature 059 pass at the
  recorded rate.

## Assumptions

- Feature 055 provides adapter open, DXGI presentation and private data;
  feature 053 provides shared allocations.
- The host GPU supports the Vulkan features the translation needs; where it
  does not, the feature level is reduced, not faked.

## Out of Scope

- Direct3D 12: feature 057. Direct3D 9 through the Microsoft runtime: feature 064.
- Zero-copy composition and dmabuf scanout: feature 058.
- Video processing and decode DDIs.
- Multi-plane overlay.
