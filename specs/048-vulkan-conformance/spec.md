# Feature Specification: Vulkan: conformance and the application suite in the guest

**Feature Branch**: `048-vulkan-conformance`

**Created**: 2026-09-11

**Feature ID**: 048 · **Status**: `implement` · **Depends on**: 047

The L5 application suite: a Vulkan CTS mustpass subset, vkcube, and DXVK and
vkd3d-proton samples run in the guest by the in-guest runner, with rendered
frames compared against references and pass rates recorded as a ratchet.

### Status meaning

Build it, test it to the constitution's standard, and report the capabilities it enables.

### Design rules — binding on this feature

Constitution Principle III and [`CLAUDE.md`](../../CLAUDE.md). Restated here because it is checked at review, not assumed:

- **Every unit of behaviour is a class that owns state.** No static member functions. No stateless class used as a namespace. No free function outside the two ABI boundaries (`DxgkDdi*` entry points in `src/core/ddi/`, and `extern "C"` entry points), each one line with no logic.
- If functions thread the same handle, buffer, bounds or platform through their parameters, **that parameter is a member**. Make it a class and inject its dependencies at construction.
- Name the classes this feature adds before writing them, and say which kind each is: an **object class** (one instance per real thing) or a **system class** (a long-lived service owning a collection).
- Dependencies injected at construction. No global, no singleton, no file-scope state.
- Data members private, trailing underscore. Classes `PascalCase`, methods and locals `snake_case`. No `Manager`, `Helper`, `Utils`, `Handler`, `Impl`, `process()`, `handle()`.
- One class per header, named for it. A header declares; it does not define. One responsibility per class, statable without an "and".
- Errors are `av::Status` values. No exceptions, no RTTI, no C++ standard library, no `new`/`delete` (placement new only in `ObjectStorage`). Cleanup is RAII via `ScopeExit`, never repeated per branch.
- Fallible construction is two-phase: trivial constructor, `initialize(...)` returning `Status`.
- Every public method declares its IRQL ceiling via `platform_.require_irql_at_most(...)`.

### Test requirements

Constitution Principle III applies in full. Concretely, this feature is not done until:

- every branch of every function it adds to `src/core`, `src/device` or `src/proto` is covered, or marked `AV_UNTESTABLE` with a justification;
- each stateful module it adds exports an invariant function that tests call after **every** mutation;
- every function it adds that reads bytes from outside its own address space has a hostile-input table test and a libFuzzer target with a committed corpus;
- the allocation-failure sweep passes: with each allocation site failed in turn, no crash and no leak;
- IRQL annotations are present and the mock's IRQL checker is satisfied;
- `tools/check_symbol_tests.py` reports no untested exported symbol.

## User Scenarios & Testing *(mandatory)*

<!-- Written by /speckit-specify or by hand. The autogen block above is regenerated by tools/gen_specs.py; everything below is preserved. -->

Users: the driver's developers and anyone deciding whether the Vulkan path
can be trusted, who need a repeatable, automated answer - from a Linux host,
through the in-guest runner - to "does Vulkan in the guest behave like Vulkan
on the host", rather than one sample that happened to render. No Vulkan
conformance run exists in render-server or here today.

### User Story 1 - A Vulkan CTS mustpass subset in the guest (Priority: P1)

**Independent Test**: the in-guest runner, given a pinned Vulkan CTS build and
a subset list, runs it in the guest on rvkgpu, pulls the results into its work
directory, and compares them with the same subset run natively on the host
GPU; the comparison, not the absolute pass count, is the verdict.

**Acceptance Scenarios**:

1. **Given** a prepared image and the package, **When** the runner is asked for
   the Vulkan suite, **Then** it pushes the CTS binaries and the subset, runs
   them with a per-test timeout, and pulls `TestResults.qpa` and logs into
   `diag/`.
2. **Given** results from the guest and from the host, **When** they are
   compared, **Then** every test that passes on the host and fails, crashes or
   times out in the guest is listed by name, and the run fails.
3. **Given** a test that fails on the host too, **Then** it is recorded but
   does not fail the run.
4. **Given** a crash in the guest process or a TDR during a test, **Then** the
   runner records the test, collects the guest's diagnostics, and continues
   with the next test.

### User Story 2 - The application suite (Priority: P1)

**Independent Test**: vkcube, the Vulkan probe of feature 045, and pinned DXVK
and vkd3d-proton samples run in the guest; the runner captures frames at fixed
points and compares them against committed reference frames with a tolerance.

**Acceptance Scenarios**:

1. **Given** each application, **When** it runs for its scripted duration,
   **Then** it exits cleanly and its captured frames match references.
2. **Given** a mismatch, **Then** the captured frame, the reference and a
   difference image are kept in the work directory.

### User Story 3 - Pass rates as a ratchet (Priority: P2)

**Independent Test**: the recorded guest-versus-host result set is committed;
a run that loses a previously passing test fails, and a run that gains one
tightens the record in the same change.

### Edge Cases

- A host GPU without an extension a CTS group needs: those tests report
  NotSupported on host and guest alike - matching, not a failure.
- Device lost mid-test: the test fails, the CTS process restarts from the next
  test, the verdict names it.
- Tests that open windows: minimize, resize and occlusion groups run on the
  guest desktop of feature 038, one output and several.
- 32-bit WoW64: the 32-bit CTS build runs a smaller subset through the 32-bit
  ICD.
- Adapter removal or a guest bugcheck mid-suite: the runner's panic and rescue
  path (feature 035's cycle) collects dumps and the suite resumes after reboot
  where it stopped.
- Memory budget exhaustion tests: out-of-memory results match the host's
  semantics, allowing for the guest's smaller budget.
- Long suites: the subset is sharded so no single guest run exceeds the
  runner's step timeout.

## Requirements *(mandatory)*

- **FR-001**: The CTS version, subset lists, DXVK and vkd3d-proton versions and
  reference frames are pinned in the repository; binaries are fetched by hash.
- **FR-002**: The verdict is guest-versus-host on the same GPU and the same
  subset, never an absolute count.
- **FR-003**: The runner gains a suite step that survives per-test crashes,
  TDRs and guest bugchecks, resuming after the failing test.
- **FR-004**: Frame capture uses the device's scanout, not a guest-side
  screenshot API, so composition problems are caught.
- **FR-005**: Every extension or feature reported by the ICD is exercised by at
  least one CTS group in the subset or by a named test in the application
  suite (constitution VI).
- **FR-006**: The suite is a `tools/gate.sh` guest step when a prepared image
  is named, as feature 035's suite is.

## Success Criteria *(mandatory)*

- **SC-001**: The mustpass subset shows no guest-only failure on every
  supported host GPU class.
- **SC-002**: Every application in the suite matches its references.
- **SC-003**: A regression introduced on purpose (an extension feature bit
  cleared) fails the suite with the test named.

## Assumptions

- The host can run the same CTS natively on the same GPU for comparison.
- The guest image has room for the CTS binaries; they are pushed per run and
  never baked into the image.

## Out of Scope

- Khronos conformance submission and official conformant status.
- Performance measurement (062); OpenGL and OpenCL conformance (054); D3D
  conformance (059).
