# Feature Specification: One adapter per host GPU in the guest

**Feature Branch**: `060-multi-gpu-live`

**Created**: 2026-09-11

**Status**: Draft

<!-- AUTOGEN:BEGIN -->

**Feature ID**: 060 · **Status**: `implement` · **Depends on**: 048

Several virtio-gpu-rvk-pci devices, one per host GPU, each an rvkgpu adapter
the guest sees as its own GPU: LUIDs that match across Vulkan, OpenGL, OpenCL,
DXGI and DXCore, per-adapter memory budgets and Task Manager engines, and
D3D12 and Vulkan applications choosing between them.

### Status meaning

Build it, test it to the constitution's standard, and report the capabilities it enables.

### Design rules — binding on this feature

Constitution Principle III and [`CLAUDE.md`](../../CLAUDE.md). Restated here because it is checked at review, not assumed:

- **Every unit of behaviour is a class that owns state.** No static member functions. No stateless class used as a namespace. No free function outside the two ABI boundaries (`DxgkDdi*` entry points in `src/core/ddi/`, and `extern "C"` entry points), each one line with no logic.
- If functions thread the same handle, buffer, bounds or platform through their parameters, **that parameter is a member**. Make it a class and inject its dependencies at construction.
- Name the classes this feature adds before writing them, and say which kind each is: an **object class** (one instance per real thing) or a **system class** (a long-lived service owning a collection).
- Dependencies injected at construction. No global, no singleton, no file-scope state.
- Data members private, trailing underscore. Classes `PascalCase`, methods and locals `snake_case`. No `Manager`, `Helper`, `Utils`, `Handler`, `Impl`, `process()`, `handle()`.
- One class per header, named for it. A header declares; it does not define. One responsibility per class, statable without an "and".
- Errors are `av::Status` values. No exceptions, no RTTI, no C++ standard library, no `new`/`delete` (placement new only in `ObjectStorage`). Cleanup is RAII via `ScopeExit`, never repeated per branch.
- Fallible construction is two-phase: trivial constructor, `initialize(...)` returning `Status`.
- Every public method declares its IRQL ceiling via `platform_.require_irql_at_most(...)`.

## User Scenarios & Testing *(mandatory)*

<!-- Written by /speckit-specify or by hand. The autogen block above is regenerated by tools/gen_specs.py; everything below is preserved. -->

Users: people running a Windows guest on a host with more than one GPU - a
laptop with an integrated and a discrete GPU, a workstation with two cards - who
expect Windows to see each host GPU as its own GPU, the way it would on bare
metal, and applications to choose between them. Also the developers of this
project, whose host (an Intel Iris Xe on Mesa and an NVIDIA RTX 3070 Ti Laptop
GPU) is the two-GPU test bed.

### User Story 1 - Every host GPU is its own guest adapter (Priority: P1)

**Independent Test**: the in-guest runner boots the prepared image with one
`virtio-gpu-rvk-pci` per host GPU, generated by `tools/host/list_gpus`, and a
guest program reports one rvkgpu adapter per device, each started with no
problem code, each with its own LUID and the host GPU identity its capset carries.

**Acceptance Scenarios**:

1. **Given** a host with N Vulkan physical devices, **When** `tools/host/list_gpus
   --qemu` generates the configuration and the guest boots, **Then** Device
   Manager shows N started rvkgpu adapters, one `rvkgpu.sys` instance each.
2. **Given** each adapter, **When** D3DKMT enumerates adapters, **Then** each
   reports a distinct LUID and the vendor, device and name of the host GPU its
   device is bound to by UUID.
3. **Given** the host GPUs are enumerated in a different order after a host
   reboot or driver update, **When** the guest boots with the same generated
   configuration, **Then** each adapter is bound to the same host GPU as before.
4. **Given** llvmpipe is the only host Vulkan device, **Then** exactly one
   adapter appears and every API still works on it, reporting a CPU device type.

### User Story 2 - The same GPU is the same GPU in every API (Priority: P1)

**Independent Test**: a guest program collects the adapter LUID from DXGI,
DXCore, D3DKMT, Vulkan (`VkPhysicalDeviceIDProperties::deviceLUID`), OpenCL
(`CL_DEVICE_LUID_KHR`) and OpenGL (the WGL device the ICD reports) and checks
they partition into the same adapters.

**Acceptance Scenarios**:

1. **Given** two adapters, **When** each API enumerates, **Then** every API
   lists both and the LUIDs match across APIs one to one.
2. **Given** a Vulkan application that picks the discrete GPU, **When** it
   renders, **Then** the commands execute on the host GPU of that adapter's
   device and no other, as the device-side object counts show.
3. **Given** DXGI's high-performance GPU preference, **Then** it orders the
   adapters by the device types the capsets report, not by PCI order.

### User Story 3 - Budgets and engines are per adapter (Priority: P2)

**Independent Test**: on each adapter, `D3DKMTQueryVideoMemoryInfo` and
Task Manager's GPU pages report that host GPU's memory and utilisation;
exhausting one adapter's budget does not change the other's.

**Acceptance Scenarios**:

1. **Given** two adapters with different host memory sizes, **Then** each
   reports its own dedicated and shared budgets, derived from its capset.
2. **Given** a workload on one adapter, **Then** Task Manager shows engine time
   on that adapter only.
3. **Given** an allocation pressure run on one adapter, **When** it is evicted,
   **Then** no allocation on the other adapter is touched.

### User Story 4 - Applications use several GPUs at once (Priority: P3)

**Independent Test**: a D3D12 explicit multi-adapter sample and a Vulkan
program rendering on one adapter and presenting through the other both complete
in the application suite, with frames matching their references.

**Acceptance Scenarios**:

1. **Given** a D3D12 application creating a device on each adapter and sharing a
   cross-adapter heap, **Then** it renders correctly.
2. **Given** a TDR on one adapter, **Then** the other adapter's devices and
   contexts keep running and its applications see no device loss.

### Edge Cases

- A host GPU present when the configuration was generated is absent at the next
  boot: the device fails to realize with a named error naming the UUID, and
  `list_gpus` regenerates a configuration that omits it.
- Two identical host GPUs: they differ only by UUID; each adapter binds to its
  own, and swapping PCI slots on the host does not swap guest adapters.
- One adapter's device faults or its executor is lost: only that adapter
  resets.
- More host GPUs than the guest's PCI topology allows: `list_gpus` places each
  device on its own root port and says when it runs out.
- The display is on one adapter and an application renders on the other:
  presentation crosses adapters by copy and is correct.

## Requirements *(mandatory)*

- **FR-001**: Each `virtio-gpu-rvk-pci` binds to the host physical device whose
  device UUID its `host-gpu` property names, and fails to realize with a named
  error when that device is absent; `host-gpu=auto` binds the first device.
- **FR-002**: `tools/host/list_gpus` generates one device per host GPU for QEMU
  and for libvirt, with stable ordering by UUID and one PCI root port each.
- **FR-003**: Each rvkgpu adapter reports the host GPU identity, device type
  and memory sizes its capset carries; no guest component branches on a vendor
  list.
- **FR-004**: The adapter LUID is the single identity every guest API exposes
  for an adapter; the ICDs and the UMD report it and nothing else.
- **FR-005**: Memory budgets, residency, eviction and engine accounting are per
  adapter.
- **FR-006**: A fault, TDR or reset on one adapter leaves every other adapter's
  devices, contexts and allocations untouched.
- **FR-007**: The in-guest runner accepts several host GPUs and its application
  suite includes the multi-adapter scenarios above.

## Success Criteria *(mandatory)*

- **SC-001**: On the two-GPU host, the in-guest runner reports two adapters,
  matching LUIDs across all APIs, and a passing multi-adapter scenario set.
- **SC-002**: A run with one host GPU hidden from QEMU fails at realize with the
  named error, and the regenerated configuration boots with one adapter.
- **SC-003**: A TDR injected on one adapter leaves the other adapter's workload
  completing with frames matching its reference.

## Assumptions

- The host exposes each GPU as its own Vulkan physical device with a stable
  device UUID, and llvmpipe is available when no GPU is.
- Windows treats separate WDDM adapters as separate GPUs for DXGI, DXCore,
  D3D12 multi-adapter and Task Manager; linked adapters are not needed.
- Features 045, 050 and 052 report adapter LUIDs; 055 reports them to DXGI.

## Out of Scope

- WDDM linked adapters and any single adapter fronting several host GPUs.
- Hot-plugging a GPU into a running guest.
- Splitting one host GPU into several guest adapters, and GPU partitioning or
  SR-IOV reporting (declined in feature 025).
- Choosing a host GPU on the guest's behalf beyond the capset's device type.
