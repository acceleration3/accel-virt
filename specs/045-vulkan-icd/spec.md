# Feature Specification: Vulkan: the ICD on rvkgpu

**Feature Branch**: `045-vulkan-icd`

**Created**: 2026-09-11

**Status**: Draft

<!-- AUTOGEN:BEGIN -->

**Feature ID**: 045 · **Status**: `implement` · **Depends on**: 044

This project's generated Vulkan ICD over the guest transport, found by the
Vulkan loader through the adapter's driver registration rather than a global
key: each physical device is one rvkgpu adapter with its LUID, memory types
come from the adapter's segments and budgets, timeline semaphores and fences
wait on rvk fences, and a TDR or fault reports VK_ERROR_DEVICE_LOST. Vulkan
1.3, or the host's version if lower.

### Status meaning

### Carried from feature 044: the memory round trip

Feature 044 proved the Vulkan object chain from a guest process on the host GPU
but could not prove its US1.2 - a buffer in host-visible memory, a pattern written
and read back in the guest - because `vkMapMemory` is off the wire and nothing
ties a guest-mapped allocation to the executor's `VkDeviceMemory` (044
research §3). Mapping is this feature's memory model (FR-003), so the scenario is
this feature's to demonstrate: a pattern the application writes through a mapped
`VkDeviceMemory` is the pattern the host GPU reads, and the reverse.

## User Scenarios & Testing *(mandatory)*

<!-- Written by /speckit-specify or by hand. The autogen block above is regenerated by tools/gen_specs.py; everything below is preserved. -->

Users: Vulkan applications in the Windows guest - and, through feature 047,
DXVK and vkd3d-proton - that must find the host GPU as an ordinary Vulkan
physical device the moment the driver package is installed, with no
environment variable, no global registry key and no DLL placed beside them;
and the developers who need a Vulkan failure in the guest to be as diagnosable
as one on the host.

### User Story 1 - The loader finds the adapter's ICD (Priority: P1)

**Independent Test**: in the guest, with the driver package installed and no
`VK_DRIVER_FILES`, `VK_ICD_FILENAMES` or `HKLM\SOFTWARE\Khronos\Vulkan\Drivers`
entry for the ICD, a probe program lists exactly one rvk physical device per
rvkgpu adapter, and its `deviceLUID` equals the LUID `D3DKMTEnumAdapters2`
reports for that adapter.

**Acceptance Scenarios**:

1. **Given** rvkgpu installed on one adapter, **When** the Vulkan loader
   enumerates physical devices, **Then** it loads render-server's ICD from the
   adapter's driver registration (`VulkanDriverName` in the display adapter's
   software key) and the ICD reports one physical device bound to that adapter.
2. **Given** that physical device, **When** its properties are queried,
   **Then** `deviceName`, `vendorID`, `deviceID` and `driverVersion` describe the
   host GPU from the adapter's capset, `deviceType` is the host's type,
   `deviceLUIDValid` is true, and `apiVersion` is 1.3 or the host's version if
   lower.
3. **Given** the ICD negotiates the loader interface, **When** the loader
   offers a version, **Then** the ICD accepts the highest version it implements
   and fails negotiation cleanly for one it does not.
4. **Given** an adapter whose device offers no Vulkan sub-API in its capset,
   **Then** the ICD reports no physical device for it and the loader continues
   with other drivers.

### User Story 2 - A Vulkan device runs on the host GPU (Priority: P1)

**Independent Test**: the probe creates an instance, a device with every queue
family the host exposes, allocates memory of each type, records and submits a
compute and a graphics workload, and reads back correct results - with the
in-guest runner confirming (from the device's log) that commands crossed an rvk
context ring and not a shared-memory region.

**Acceptance Scenarios**:

1. **Given** a device, **When** memory is allocated, **Then** memory types map
   to rvkgpu segments - device-local memory to the aperture-less segment,
   host-visible memory to the host-visible segment of feature 041 - and
   `vkMapMemory` on host-visible memory returns a pointer that reads and writes
   the host GPU's memory without a copy.
2. **Given** `VK_EXT_memory_budget`, **When** heaps are queried, **Then** budget
   and usage match `D3DKMTQueryVideoMemoryInfo` for the adapter within one
   allocation's size.
3. **Given** a submission and a timeline semaphore or fence, **When** the host
   completes the work, **Then** the wait returns on the rvk fence without
   polling, and `vkWaitForFences` with a timeout returns `VK_TIMEOUT` on time.
4. **Given** a device whose context faults or whose adapter goes through TDR,
   **When** the application next submits or waits, **Then** it receives
   `VK_ERROR_DEVICE_LOST`, and destroying and recreating the device works.

### User Story 3 - Only what is real is reported (Priority: P1)

**Independent Test**: for each host GPU class in the device test matrix, the
reported extension and feature set equals render-server's generated allowlist
intersected with what the host device reports, minus what this path does not
yet implement; a test enables each reported extension and exercises it.

**Acceptance Scenarios**:

1. **Given** a host GPU without an extension, **When** the guest enumerates
   device extensions, **Then** that extension is absent and creating a device
   with it fails with `VK_ERROR_EXTENSION_NOT_PRESENT`.
2. **Given** WSI extensions, **Then** they are reported by the ICD itself, never
   forwarded to the host (presentation is feature 046).

### Edge Cases

- A host GPU that lacks an extension the allowlist names: absent in the guest.
- Device lost mid-frame: in-flight fences complete as lost, mapped pointers
  stay readable until unmap, no guest process crashes.
- Two applications and a WoW64 32-bit application at once: each gets its own
  contexts; the 32-bit ICD (`VulkanDriverNameWow`) maps host-visible memory
  below 4 GiB.
- Adapter removal (device disabled or driver upgraded) while an instance
  exists: physical devices of that adapter report device lost; enumeration
  after removal no longer lists them.
- Memory budget exhausted: allocation returns `VK_ERROR_OUT_OF_DEVICE_MEMORY`,
  never succeeds with memory the host cannot back.
- Several adapters (feature 060): each physical device's LUID matches its own
  adapter.
- The ICD registered globally as well as through the adapter: the loader must
  not list the device twice; the package registers only through the adapter.

## Requirements *(mandatory)*

- **FR-001**: The ICD is discovered only through the adapter's driver
  registration; installation writes no global Khronos key.
- **FR-002**: Every command crosses the guest transport of feature 043; the ICD
  contains no shared-memory-region transport in this configuration.
- **FR-003**: Memory types, heaps and budgets derive from the adapter's segments
  and `D3DKMTQueryVideoMemoryInfo`, not from host numbers passed through.
- **FR-004**: Reported extensions and features are the intersection of the
  generated allowlist, the host device, and what this path implements and
  tests (constitution VI).
- **FR-005**: Device loss - context fault, TDR, adapter removal - surfaces as
  `VK_ERROR_DEVICE_LOST` on the next call that can return it.
- **FR-006**: Guest-side ICD logic that is not generated code is testable on
  Linux against the loopback rig of feature 034, including device-lost paths.
- **FR-007**: The ICD's log reaches the in-guest runner's `diag/` for every run.

## Success Criteria *(mandatory)*

- **SC-001**: On a clean guest with the package, `vulkaninfo` lists the rvk
  device with the adapter's LUID; no Khronos global key exists.
- **SC-002**: The probe's compute and graphics workloads pass on every host GPU
  class the device supports, through rvk contexts only.
- **SC-003**: A forced context fault yields `VK_ERROR_DEVICE_LOST` and a
  recreated device works, in the same process.

## Assumptions

- render-server's Vulkan ICD accepts a transport handed to it (the contract of
  feature 043) and keeps its generated allowlist.
- Feature 044 has proven rvk contexts end to end on the real executor.

## Out of Scope

- Presentation (046), the DXVK/vkd3d-proton feature set (047), conformance runs
  (048), doorbells on the hot path (049), cross-process sharing (053).
- Vulkan video, ray tracing beyond what the allowlist names, and versions above
  1.3.
