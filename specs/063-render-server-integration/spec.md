**Feature ID**: 063 · **Status**: `implement` · **Depends on**: 001, 032

render-server pinned by revision and hash like QEMU and the Windows kit, and
built from this repository's build: its Vulkan, OpenGL and OpenCL guest
drivers for Windows x64 and x86, and its host executor library with a pkg-
config file. The seam changes this project needs of it - a C-ABI executor over
its server backends, a link built over a transport it is handed, and an OpenGL
client an ICD front end can drive - are carried as a patch series with tests
and sent upstream, so the pin can return to a plain revision.

### Status meaning

Build it, test it to the constitution's standard, and report the capabilities it enables.

### Note

Numbered last because it was identified last; 042 and 043 depend on it, so the
roadmap schedules it before them.

### Design rules — binding on this feature

Constitution Principle III and [`CLAUDE.md`](../../CLAUDE.md). Restated here because it is checked at review, not assumed:

- **Every unit of behaviour is a class that owns state.** No static member functions. No stateless class used as a namespace. No free function outside the two ABI boundaries (`DxgkDdi*` entry points in `src/core/ddi/`, and `extern "C"` entry points), each one line with no logic.
- If functions thread the same handle, buffer, bounds or platform through their parameters, **that parameter is a member**. Make it a class and inject its dependencies at construction.
- Name the classes this feature adds before writing them, and say which kind each is: an **object class** (one instance per real thing) or a **system class** (a long-lived service owning a collection).
- Dependencies injected at construction. No global, no singleton, no file-scope state.
- Data members private, trailing underscore. Classes `PascalCase`, methods and locals `snake_case`. No `Manager`, `Helper`, `Utils`, `Handler`, `Impl`, `process()`, `handle()`.
- One class per header, named for it. A header declares; it does not define. One responsibility per class, statable without an "and".
- Errors are `av::Status` values. No exceptions, no RTTI, no C++ standard library, no `new`/`delete` (placement new only in `ObjectStorage`). Cleanup is RAII via `ScopeExit`, never repeated per branch.
- Fallible construction is two-phase: trivial constructor, `initialize(...)` returning `Status`.
- Every public method declares its IRQL ceiling via `platform_.require_irql_at_most(...)`.

### Test requirements

Constitution Principle III applies in full. Concretely, this feature is not done until:

- every branch of every function it adds to `src/core`, `src/device` or `src/proto` is covered, or marked `AV_UNTESTABLE` with a justification;
- each stateful module it adds exports an invariant function that tests call after **every** mutation;
- every function it adds that reads bytes from outside its own address space has a hostile-input table test and a libFuzzer target with a committed corpus;
- the allocation-failure sweep passes: with each allocation site failed in turn, no crash and no leak;
- IRQL annotations are present and the mock's IRQL checker is satisfied;
- `tools/check_symbol_tests.py` reports no untested exported symbol.

## User Scenarios & Testing *(mandatory)*

Users: the developers of this repository, who need serialization for three
graphics APIs that is generated rather than hand-written, and generated by
something this project owns.

**What changed, and why this spec was rewritten.** The feature was first
written as "render-server as a pinned build input": fetch its tree, carry a
patch series, build its guest drivers and its server backends. That is not what
this project wants. **Only the generators are taken. None of render-server's
code is.** The generator is vendored into this repository and owned here; the
C++ it emits is this project's, committed and reviewed like any other source;
the runtime that uses it - the guest drivers, the host executor, the transport -
is written here, against this project's own ABIs.

### User Story 1 - The generator is ours (Priority: P1)

**Independent Test**: from a clean checkout, running the generator over the
pinned Khronos registries reproduces every committed generated file byte for
byte, and a deliberate edit to a generated file fails the gate naming it.

**Acceptance Scenarios**:

1. **Given** the vendored generator, **When** it is run against the registries
   for Vulkan, OpenGL and OpenCL, **Then** it writes this project's
   serialization, dispatch and protocol-id sources into the committed tree.
2. **Given** a committed generated tree, **When** the gate runs, **Then** it
   re-runs the generator into a temporary directory and fails on any difference,
   naming the file - the same check the generator's `--check` already performs.
3. **Given** no fetched registries, **When** the gate runs, **Then** it says it
   skipped and why; the build itself never needs them, because what the build
   compiles is committed.
4. **Given** a change to the generator, **When** it is committed, **Then** the
   regenerated sources are committed in the same change, and the gate proves
   they agree.

### User Story 2 - The registries are pinned inputs (Priority: P1)

**Independent Test**: the fetch tool retrieves each registry at its pinned
revision, verifies it by hash, and a changed hash fails the fetch with a named
error, unpacking nothing.

**Acceptance Scenarios**:

1. **Given** a clean checkout, **When** the fetch tool runs, **Then** `vk.xml`,
   `gl.xml` and `cl.xml` are fetched at pinned revisions, verified by hash and
   unpacked under `third_party/` (git-ignored); a second fetch is a no-op.
2. **Given** an unreachable source or a hash that does not match, **When** the
   fetch runs, **Then** it names what failed and leaves any previously verified
   tree untouched.

### User Story 3 - What the generated code has to satisfy (Priority: P1)

**Independent Test**: the generated sources compile under this repository's
flags for both the device side and the guest side, and the gates that judge
hand-written code do not judge machine-written code by rules it cannot keep.

**Acceptance Scenarios**:

1. **Given** the generated sources, **When** the build runs, **Then** they
   compile with this repository's warnings-as-errors, with no exceptions and no
   RTTI, and link into both the device build and the guest build.
2. **Given** the design and coverage gates, **When** they run, **Then**
   generated directories are excluded by a rule that names them, and the
   hand-written code that calls into them is held to the full standard.
3. **Given** a decoder that reads bytes it did not write, **Then** a fuzz target
   drives it with a committed corpus, because generated code is exactly where a
   hostile frame lands first.

### Edge Cases

- A registry moves a command between extensions, or renames one: the regenerated
  output differs, the gate fails, and the change is reviewed as a wire change.
- The profile selects a command the registry does not define: the generator
  fails naming it rather than emitting a stub.
- Two APIs claim the same protocol id: the generator refuses, because an id
  collision is a frame decoded as the wrong command.
- The generator needs a Python version or package the machine lacks: the gate
  says which, and skips rather than failing the build.
- A generated file grows beyond what a compiler will take in one translation
  unit: the generator splits it, and the split is part of the committed output.

## Requirements *(mandatory)*

- **FR-001**: The generator is vendored under this repository, owned here, and
  no render-server source is used at build time or runtime.
- **FR-002**: The Khronos registries are fetched by revision and verified by
  hash, like `tools/fetch_qemu.sh`; no tracked file names a path outside this
  repository (the `self_contained` gate).
- **FR-003**: Every generated source is committed, and a gate re-runs the
  generator and fails on any difference.
- **FR-004**: Generated sources compile under this repository's flags for the
  device build and the guest build.
- **FR-005**: The design and coverage gates exclude generated directories by an
  explicit rule, and nothing hand-written hides in one.
- **FR-006**: Whatever the generated decoders read from outside has a fuzz
  target with a committed corpus.
- **FR-007**: The protocol ids the generator assigns are the ones
  `docs/protocol.md` documents, and a change to either fails the gate until both
  agree.

## Success Criteria *(mandatory)*

- **SC-001**: A clean checkout plus a fetch reproduces every committed generated
  file byte for byte.
- **SC-002**: The generated Vulkan, OpenGL and OpenCL serialization compiles and
  links into both builds, with the image gates passing for the guest artefacts.
- **SC-003**: A deliberate edit to any generated file is caught by the gate,
  naming the file.

## Assumptions

- The Khronos registries remain fetchable by revision from their repositories.
- render-server's generator is a Python package that can be lifted out of its
  tree and run on its own; what it needs beyond the registries are profile and
  protocol-id files, which become this repository's to edit.

## Out of Scope

- Any use of render-server's runtime: its client drivers, its server backends,
  its transport and its shared-memory link. Features 042 and 043 describe those
  as render-server's today and will be corrected to say this project writes
  them, against the generated wire.
- The guest drivers and the host executor themselves (042, 043, 045, 050, 052).
- Upstreaming anything to render-server.
