# 02 — The KMD contract

## Registration

A WDDM miniport is a normal kernel driver whose `DriverEntry` does *not* fill
in the usual `DRIVER_OBJECT` dispatch table. Instead it fills a
`DRIVER_INITIALIZATION_DATA` and hands it to `dxgkrnl`:

```c
NTSTATUS DriverEntry(PDRIVER_OBJECT DriverObject, PUNICODE_STRING RegistryPath)
{
    DRIVER_INITIALIZATION_DATA init = {0};

    init.Version = DXGKDDI_INTERFACE_VERSION_WDDM3_2;   /* 0x11007 */

    init.DxgkDdiAddDevice            = MyAddDevice;
    init.DxgkDdiStartDevice          = MyStartDevice;
    init.DxgkDdiStopDevice           = MyStopDevice;
    init.DxgkDdiRemoveDevice         = MyRemoveDevice;
    init.DxgkDdiDispatchIoRequest    = MyDispatchIoRequest;
    init.DxgkDdiInterruptRoutine     = MyInterruptRoutine;
    init.DxgkDdiDpcRoutine           = MyDpcRoutine;
    init.DxgkDdiQueryChildRelations  = MyQueryChildRelations;
    init.DxgkDdiQueryChildStatus     = MyQueryChildStatus;
    init.DxgkDdiQueryDeviceDescriptor= MyQueryDeviceDescriptor;
    init.DxgkDdiSetPowerState        = MySetPowerState;
    init.DxgkDdiUnload               = MyUnload;
    init.DxgkDdiQueryInterface       = MyQueryInterface;
    init.DxgkDdiControlEtwLogging    = MyControlEtwLogging;
    init.DxgkDdiQueryAdapterInfo     = MyQueryAdapterInfo;
    /* … and ~170 more slots … */

    return DxgkInitialize(DriverObject, RegistryPath, &init);
}
```

`DxgkInitialize` replaces the driver object's dispatch routines with
`dxgkrnl`'s own, so from that point on every IRP goes to `dxgkrnl` first and
reaches you only as a DDI callback.

`Version` is the *entire* version negotiation. There is no feature-bit
handshake at this level: you claim a DDI level and `dxgkrnl` then assumes every
slot up to that level is either a valid pointer or `NULL`, and that your
structure layouts match that level's headers. Claim `WDDM3_2` and you must
build against `DXGKDDI_INTERFACE_VERSION == 0x11007` headers or the struct
offsets will be wrong.

The full table - 193 fields: `Version`, 187 DDIs and 5 `Reserved` pointers - with each slot's introducing version is in
[`docs/ref/driver_init_table.md`](../ref/driver_init_table.md), generated by
`tools/re/ddi_extract.py`.

## Which slots are actually mandatory

`dxgkrnl` NULL-checks most optional DDIs, but a render-capable miniport that
leaves a required slot NULL fails to start with no useful message. The
practical minimum, taken from what `basicrender.sys` fills in:

**PnP and lifetime** — `AddDevice`, `StartDevice`, `StopDevice`,
`RemoveDevice`, `DispatchIoRequest`, `Unload`, `SetPowerState`,
`QueryChildRelations`, `QueryChildStatus`, `QueryDeviceDescriptor`,
`QueryInterface`, `ControlEtwLogging`.

**Interrupt path** — `InterruptRoutine`, `DpcRoutine`. Even with no real
hardware interrupt you need these; you raise completions by calling
`DxgkCbNotifyInterrupt` followed by `DxgkCbQueueDpc`, and `dxgkrnl` reflects
them back through your DPC routine.

**Capability reporting** — `QueryAdapterInfo`. This one DDI is a 48-way switch
(see `DXGKQAITYPE_*`) and is where you describe segments, GPU MMU capabilities,
node count, native fence support, and everything else. Getting it wrong is the
most common cause of "the driver loaded and D3D12 still refuses to create a
device".

**Device and allocation** — `CreateDevice`, `DestroyDevice`,
`CreateAllocation`, `DestroyAllocation`, `DescribeAllocation`,
`GetStandardAllocationDriverData`, `OpenAllocation`, `CloseAllocation`.

**Execution** — `CreateContext`, `DestroyContext`, `Render` (and/or
`RenderKm`), `Patch` *or* GPU-VA mode, `SubmitCommand` /
`SubmitCommandVirtual`, `PreemptCommand`, `QueryCurrentFence`,
`ResetFromTimeout`, `RestartFromTimeout`, `CancelCommand`,
`QueryEngineStatus`, `ResetEngine`, `QueryDependentEngineGroup`,
`BuildPagingBuffer`.

**Process objects** — `CreateProcess`, `DestroyProcess` (WDDM 2.0+).

**Display** — the whole `VidPn` family plus `SetVidPnSourceAddress` /
`SetVidPnSourceVisibility`, `CommitVidPn`, `IsSupportedVidPn`,
`RecommendFunctionalVidPn`, `EnumVidPnCofuncModality`, `Present` /
`PresentDisplayOnly`, `ControlInterrupt`.

## Capability reporting: `DxgkDdiQueryAdapterInfo`

One callback, 48 query types. The ones that decide whether you are a modern
driver at all:

| Query type | What it decides |
|---|---|
| `DXGKQAITYPE_DRIVERCAPS` | `DXGK_DRIVERCAPS` — the master capability block: highest supported DDI level behaviours, `SchedulingCaps`, `MemoryManagementCaps`, `GpuEngineTopology.NbAsymetricProcessingNodes`, preemption granularity, flip caps. |
| `DXGKQAITYPE_QUERYSEGMENTCOUNT` / `QUERYSEGMENT5` | The memory segments you expose to VidMm. `…5` is the current revision. |
| `DXGKQAITYPE_GPUMMUCAPS` | `DXGK_GPUMMUCAPS` — do you support GPU virtual addressing, how many page-table levels, page sizes. Setting this is what switches you from `DxgkDdiPatch` physical addressing to the virtual model. |
| `DXGKQAITYPE_PAGETABLELEVELDESC` | Per-level page table geometry, once GPU MMU is claimed. |
| `DXGKQAITYPE_NATIVE_FENCE_CAPS` | WDDM 3.1+ native fence support. |
| `DXGKQAITYPE_USERMODESUBMISSION_CAPS` | Whether user mode may ring doorbells directly. |
| `DXGKQAITYPE_WDDMDEVICECAPS` | Per-device feature flags the runtime reads back. |
| `DXGKQAITYPE_PHYSICALADAPTERCAPS` | Multi-physical-adapter (linked) topology. |
| `DXGKQAITYPE_GPUPCAPS` | GPU partitioning (SR-IOV) capabilities. |
| `DXGKQAITYPE_DIRTYBITTRACKINGCAPS` | WDDM 3.2 dirty-bit tracking, used for live migration. |
| `DXGKQAITYPE_IOMMU_CAPS` | Whether the GPU sits behind an IOMMU. Relevant when the "GPU" is a virtio device. |

**Design note for a paravirtual driver:** answer `DXGKQAITYPE_DRIVERCAPS` and
`GPUMMUCAPS` first and get them stable before anything else. Every later
decision — physical vs virtual addressing, whether `Patch` is ever called,
whether hardware queues are legal — follows from those two answers.

## Calling back into dxgkrnl

`DXGKRNL_INTERFACE` is handed to you in `DxgkDdiStartDevice`. Keep it; it is
how you initiate anything. The ones that matter most:

| Callback | Use |
|---|---|
| `DxgkCbNotifyInterrupt` | Report a completed fence/packet from your ISR (or a synthetic ISR). |
| `DxgkCbQueueDpc` | Ask for your DPC to run after the notify. |
| `DxgkCbNotifyDpc` | Report completion at DPC level. |
| `DxgkCbMapMemory` / `UnmapMemory` | Map device memory into kernel or user space. |
| `DxgkCbGetHandleData` / `GetHandleParent` / `EnumHandleChildren` | Walk the allocation handle tree during `Render`/`Patch`. |
| `DxgkCbGetCaptureAddress` | For capture buffers. |
| `DxgkCbCreateContextAllocation` | Allocate context-private memory VidMm will manage. |
| `DxgkCbAcquireHandleData` | Safe handle→driver-data lookup outside the DDI that gave you the handle. |
| `DxgkCbLogEtwEvent` | ETW. Worth wiring early; `dxgkrnl`'s own ETW is how you debug scheduling. |

## Where the IRQL rules bite

Every DDI prototype in `d3dkmddi.h` carries an SAL `_IRQL_requires_` or
`_IRQL_requires_max_` annotation. Three groups:

- `PASSIVE_LEVEL` — creation, destruction, VidPn, `QueryAdapterInfo`. You may
  block here, take mutexes, do I/O. **This is the only place a paravirtual
  driver may wait on the host.**
- `DISPATCH_LEVEL` — `SubmitCommand`, `Patch`, `PreemptCommand`,
  `QueryCurrentFence`, `BuildPagingBuffer`. No blocking, no paged pool.
  Submission to the host from here must be a non-blocking ring write plus a
  doorbell store.
- `HIGH_LEVEL` / device IRQL — `InterruptRoutine`. Almost nothing is legal.

A design that needs to wait for a host reply inside `SubmitCommand` is wrong
and will bugcheck under load. Submission must be fire-and-forget; completion
comes back asynchronously and is reported through `DxgkCbNotifyInterrupt`.
